## Custom SQLSTATEs

Raised by the S-02 guard triggers (`supabase/migrations/20260927120000_projects_and_milestones.sql`) and the S-03 guard triggers (`supabase/migrations/20260929120000_employees_and_engagements.sql`). PostgREST passes them through unchanged in the error `code`; the app maps each to a catalog code. The `MR` prefix avoids PostgREST's reserved `PT` codes.

| SQLSTATE | Catalog code                         | Raised when                                                                                                                                                                                                                               |
| -------- | ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `MR001`  | `owner_not_supervisor`               | a project's or an employee's `supervisor_id` does not reference a Supervisor                                                                                                                                                              |
| `MR002`  | `milestone_outside_project`          | a milestone's period falls outside its project's period                                                                                                                                                                                   |
| `MR003`  | `project_closed`                     | a milestone is inserted or updated while its project is `completed` or `cancelled`                                                                                                                                                        |
| `MR004`  | `project_period_excludes_milestones` | a project date change would leave any of its milestones outside                                                                                                                                                                           |
| `MR005`  | `supervisor_owns_projects`           | the role of a Supervisor who owns projects or employees is changed                                                                                                                                                                        |
| `MR006`  | not user-reachable (`save_failed`)   | a milestone's `project_id` is changed                                                                                                                                                                                                     |
| `MR007`  | `milestone_closed`                   | an engagement is inserted, updated or deleted while its milestone or project is `completed` or `cancelled`                                                                                                                                |
| `MR008`  | `employee_has_open_engagements`      | an employee's owner changes while they are assigned to an open milestone of another Supervisor                                                                                                                                            |
| `MR009`  | `email_locked`                       | an employee's email changes after the first invite                                                                                                                                                                                        |
| `MR010`  | `job_role_archived`                  | an employee is given an archived job role                                                                                                                                                                                                 |
| `MR011`  | `employee_not_available`             | an engagement's employee is not owned by the Supervisor who owns the milestone's project                                                                                                                                                  |
| `MR012`  | `project_has_foreign_engagements`    | a project's owner changes while an open milestone of it has an engagement of an employee the new owner does not own (`projects_check_engaged_owner_change`, `supabase/migrations/20260930120000_projects_guard_engaged_owner_change.sql`) |

Known gap: reopening a completed milestone is not guarded, so an employee moved while the milestone was closed can end up engaged on another Supervisor's open milestone.

`milestones_check_parent` raises `42501` before `MR002`/`MR003` when a caller with a JWT does not own the parent project (`supabase/migrations/20260927130000_milestones_guard_ownership.sql`), so the guards never reveal another project's status or period. The S-03 guards follow the same rule: `employees_check_rules` and `milestone_engagements_check_parent` raise `42501` first, and the services map `42501` to `not_found`. MR001 and MR005 now also cover employees; `MR001`–`MR006` keep their S-02 meaning for projects and milestones.

Deleting an auth user who still owns projects or employees fails with a foreign-key violation (`projects.supervisor_id` and `employees.supervisor_id` are `on delete restrict`), just as changing their role fails with `MR005`: reassign their projects and employees first.

## Policy conventions

- Role checks in policies call the helpers wrapped in a sub-select, e.g. `using ((select public.is_admin()))`, so Postgres evaluates them once per statement. Never sub-select `public.profiles` inline in a policy (it recurses into the profiles policies).
- Enable RLS in the migration that creates the table, with one policy per operation per role and no `for all` policies.
- Views over RLS-protected tables are created with `security_invoker = true`.
- Delete policies are the exception. The first is `milestone_engagements_delete_supervisor` (the owning Supervisor, via `owns_milestone`); hard delete is allowed only while the milestone and project are open, which the guard trigger enforces (`MR007`), not the policy. Every other table has no delete policy and is archived, cancelled or kept instead.
- Columns written only by the system (`employees.profile_id`, `invited_at`, `activated_at`) and immutable keys (`milestone_engagements.milestone_id`, `employee_id` on update) are protected with column-level grants: revoke table-level `insert`/`update` from `authenticated`, then grant back only the user-editable columns. System writes go through the secret-key Edge Function or a security definer trigger.
- Structural RLS tests (pgTAP) live in `supabase/tests/` and run in CI via `supabase test db`.

## Config snapshot rule

- Computations read `public.bonus_settings` and `public.job_roles` at compute time; the config itself is not versioned.
- S-04/S-05 result rows must persist the role weight, rating factor, milestone multiplier and bonus they used, so later config edits never change Approved milestones.
- Archived job roles stay readable (existing references keep resolving). New assignments must pick only rows with `archived_at is null`.

## Money rule

- Money has two decimals (`numeric(12,2)`) and is always `> 0` where stored as a budget or pool.
- Computed money is floored to the grosz (0.01) with `public.money_floor_mul`. Never rely on a `numeric(p,2)` cast to round: it rounds half away from zero.
- Input with more than two decimals is rejected, not rounded.
